`main` was set back to the tree of **`ca450b2`**, because audio stopped working on iOS and three
attempts to find the cause by reasoning about the diff were wrong. This is the index of everything
that came out, so it can go back in one piece at a time with a device test between each.

**Nothing is deleted.** Every commit below is still in the history, and the working state at the
moment of the revert — including uncommitted work — is on the branch

## Why `ca450b2` is the target

It is the build verified on an iPhone on **2026-09-04** — takes recorded, played back, recording
offset judged by ear — plus the two fixes that came out of that same session:

- **the take-id collision**, which was silent data loss (`layer-0-take-1` in every project, so a
  second project overwrote the first project's audio);
- **the first round of zoom suppression**.

Reverting past it would reintroduce a bug that destroys recordings, so it is the earliest sane
target rather than the exact commit that was tested (`e8f567f`).

**Only two of the twenty reverted commits touched the audio path at all** — `35de75c` and
`483ede1`, both count-in:

```bash
git log --oneline ca450b2..10fec72 -- ui/src/audio.ts ui/src/app.ts ui/src/engine.ts \
  ui/src/layer-audio.ts ui/src/effects-chain.ts ui/worklets/
```

That is worth knowing before rebuilding: if audio is still broken at `ca450b2`, none of this was
ever the cause, and the eighteen UI commits can go back immediately.

- `35de75c` Count-in: two settings, a trimmed capture, and a beat indicator

- **`src/domain/count-in.ts`** — `COUNT_IN_BAR_OPTIONS` (Off · 1 · 2 · 3 · 4), `COUNT_IN_MODES`

- **The frame-space conversion in `startCapture`/`stopCapture`** (`483ede1`). Without it the trim
  subtracts a context frame from a transport frame and the count-in stays at the head of the take.
  **If `35de75c` goes back, `483ede1` must go back with it** — the first is broken without the
  second.
- **The beat pip indicator** in the lane, and the `buildLanes` re-append it needs.
- **`ui/src/verify-count-in.ts`** — `verifyCountIn` and `verifyCaptureFrames`.

## The iOS debugging work, which is NOT a feature

On the branch, uncommitted at the time it was parked:

- **`ui/audio-check.html`** — a standalone probe: no imports, no app code, so it runs when the app
  does not. Kept on `main`, because it is additive and nothing links to it. **Its first version had
  a bug that invalidated its own results**: it did `await ctx.resume()` before starting the
  oscillator, and after that await the handler is outside the user activation, so WebKit will not
  start audio. That is fixed in the copy on the branch. Any conclusion drawn from the page before
  that fix is worthless.
- **A `touchend` double-tap-zoom guard**, added and then reverted. Do not bring it back:
  `preventDefault` on a touch event takes the user activation with it, and the `AudioContext` is
  unlocked lazily from inside a tap handler.
- **A shared `AudioContext` per sample rate**, so navigation stops closing and rebuilding one.
  **Unverified, and built on a diagnosis that was later contradicted** — the probe that produced it
  had the await bug above. It may still be a good idea on its own merits. It is not evidence.

## Three wrong answers, recorded so they are not tried again

Each was argued confidently and each was wrong:

1. **The `touchend` guard silenced the app.** Disproved by the report that the Library was silent
   too — no `trackDrag` node exists on that screen, so the code could not run there.
2. **Closing the `AudioContext` per navigation silenced iOS.** Built on probe results that came
   from the probe's own await bug.
3. **The Ring/Silent switch.** The switch had been in the same position for the working tests, and
   other sites played fine.

The through-line: **an instrument that has not been checked is not evidence**, and a diff read
carefully is not a substitute for a device. The first thing to do when audio fails on the phone is
run the probe and confirm the probe itself is sound.
